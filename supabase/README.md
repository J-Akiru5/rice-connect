# Supabase (Phase 3, ticket B-01)

Local and remote database work for RiceConnect. The cloud projects are **not created yet**:
`docs/BLOCKERS.md` lists the owner actions (three projects, access token, keys).

## Layout

| Path               | What it is                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `config.toml`      | Local stack config generated by `supabase init` (CLI 2.119.0). Seed is off until B-02.   |
| `migrations/`      | The schema history (B-02 onward). Never edit a pushed migration; add a new one.          |
| `seed.sql` (later) | Dev seed, once B-02 defines the schema. Demo data stays in `packages/domain` until then. |

## Everyday commands (root)

```bash
pnpm db:start    # local Postgres + Studio (needs Docker Desktop)
pnpm db:stop
pnpm db:reset    # re-applies migrations from scratch
pnpm db:push     # applies migrations to the linked project (owner links first)
```

Create a migration after changing the schema through the Studio or SQL:

```bash
pnpm exec supabase migration new <name>
```

## Tests (B-03)

`supabase/tests/*.sql` are pgTAP suites. CI's `db` job runs them on every PR; locally:

```bash
pnpm db:start     # needs Docker Desktop
pnpm db:reset     # applies supabase/migrations from scratch
pnpm exec supabase test db
```

The suite signs in as each role (by setting `request.jwt.claims`) and checks the row-level-security
matrix from `docs/plan/03-architecture.md`. Add assertions for every new policy.

## Environments

| Environment | Branch    | Supabase                       |
| ----------- | --------- | ------------------------------ |
| Local       | any       | local stack or the dev project |
| Preview     | `staging` | staging project                |
| Production  | `main`    | production project             |

Per app, the same variable names are used locally (`.env.local`, gitignored) and on Vercel:

- `NEXT_PUBLIC_SUPABASE_URL` — safe to expose
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` — safe to expose, RLS does the access control
- `SUPABASE_SERVICE_ROLE_KEY` — **server-only, never** with a `NEXT_PUBLIC_` prefix

CLI-only variables (owner machine or CI secrets, never in the repo): `SUPABASE_ACCESS_TOKEN`,
`SUPABASE_DB_PASSWORD`, and the linked project ref (`supabase link --project-ref <ref>`).

## Rules

- Every table gets row-level security from its first migration (B-03); a per-role test runs in CI.
- No changes by hand in the dashboard: migrations in the repo are the source of truth.
- No real personal data before Phase 4 passes (`docs/plan/08-pilot-readiness.md`).
